STRICT RULES
------------
1. SOURCE AUTHORITY
   The PDF is canonical. Authored prose, authored tables, authored figures, authored formulas, and authored captions may support scientific claims. Docling and visual-recovery outputs are representations/transcriptions of those authored sources, not separate scientific authorities.

2. GENERATED VISUAL DESCRIPTIONS
   Do not treat generic/generated picture descriptions as authored scientific evidence. The bundle is designed to exclude them. If any such derived summary appears, ignore it for explicit evidence.

3. EVIDENCE TYPE VS REPRESENTATION METHOD
   Keep these independent:
   - evidence_type=explicit means the authored source directly states/shows the claim;
   - representation_method records how that authored evidence reached the extractor.
   A formula or value visibly transcribed from an authored figure may be explicit evidence with representation_method=structured_visual_recovery.

4. PROVENANCE
   For substantive claims, populate evidence records when possible. Use source_item_id/page when supplied by bundle headers such as AUTHOR_TABLE, AUTHOR_FORMULA, or AUTHOR_FIGURE. Use the corresponding source_modality and representation_method. Do not invent a page number.

5. SOURCE FIDELITY GAPS
   The bundle may list unresolved source items. Those are extraction/representation gaps. If a field is unsupported because relevant content is unresolved, use null and mention the unresolved issue in extraction_provenance. Do not infer that the canonical PDF lacks the information.

6. DATASET PROPERTIES VS DOWNSTREAM APPLICATION REQUIREMENTS
   Keep three scopes strictly separate:
   - dataset_characteristics = what the published data product IS / PROVIDES;
   - input_data_requirements = what a downstream user needs to APPLY/USE the already-published dataset in a described application/use case;
   - producer_workflow_inputs = raw observations, covariates, source archives, grids, parameters, and method-specific requirements needed to BUILD/REPRODUCE the dataset.

   Use this decision test for every candidate item:
   "If a downstream user already has the published dataset, would they still need this item to perform the described application?"
   - YES -> it may belong in input_data_requirements, if the source supports that downstream context.
   - NO, it is only needed to create/reproduce the dataset -> producer_workflow_inputs.

   For producer/data papers, default input_data_requirements to null/empty unless the source explicitly describes downstream requirements or a demonstrated downstream workflow. If a downstream use case is demonstrated, populate only the inputs consumed by that use case; do not copy the producer inputs into it.

   Generic example: if a dataset is produced from station observations + a DEM, but a downstream example combines the published raster with precipitation, then station observations + DEM are producer_workflow_inputs, while the published raster + precipitation are downstream input_data_requirements. The same item may appear in both only when the source explicitly shows that both scopes require it; the downstream entry then needs downstream-use evidence.

7. TEMPORAL GAPS
   Distinguish published_dataset_gaps from upstream_observation_gaps and broader historical_coverage_constraints.

8. PRODUCER EVIDENCE VS DOWNSTREAM EVIDENCE
   Producer-side validation is evidence about the produced dataset/modeling framework. It is not universal proof of fitness for every downstream application. Distinguish demonstrated uses from potential uses.

9. NO INVENTED THRESHOLDS
   Do not convert observed MAE/RMSE values, example uncertainties, dashed guide lines, typical ranges, or figure reference levels into formal suitability thresholds. Populate formal_thresholds or acceptable_uncertainty_levels only when the authored source explicitly defines a formal decision threshold or an externally supplied deterministic rule does so.

10. FITNESS CLASSIFICATION
    For extraction from a producer/data paper, fitness_classification and evidence_and_maturity should normally remain unassessed/unknown unless the source explicitly provides a categorical judgment or a declared deterministic decision rule is supplied. A statement such as "1 km does not resolve individual fields" can be recorded as a scale limitation; if you paraphrase it as a use limitation, mark that evidence as inferred rather than pretending the paper stated a formal fitness classification.

11. VALIDATION / PREDICTION-INTERVAL ASSESSMENT CONTEXT
    Keep selection/tuning metrics separate from in-sample diagnostics, out-of-sample validation, cross-validated prediction-interval assessment, spatial uncertainty summaries, and downstream-use-case metrics. Pearson correlation used in filter selection is not automatically an out-of-sample validation metric.

    PICP and MPIW describe empirical prediction-interval coverage and interval width/sharpness. Do not normalize their assessment as "prediction-interval calibration", "interval calibration", or equivalent wording. Use context=cross_validated_interval_assessment when that is what the authored source describes. Preserve legacy/authored wording only inside source_text/source locators when quoting the source.

    Do not imply that PICP/MPIW calibrate the published BSE layer or perform post-hoc interval calibration. Preserve the distinction between BSE/model-mean precision and prediction-interval performance.

12. SUMMARY SCOPE VS EVALUATION SUPPORT
    Keep summary scope and evaluation support separate.
    - scope describes the scientific target/aggregation summarized by the metric (e.g. dataset, dataset_family, subgroup, variable_or_layer, study_or_site, experiment_or_treatment, model_or_method, or a domain-specific scope).
    - evaluation_support describes where/how the metric was evaluated (e.g. held_out_station, raster_cell, region).
    - evaluation_population gives a concise human-readable description of those evaluated locations/population when supported.

    For station-based cross-validation, explicitly use evaluation_support=held_out_station (or observation_station when appropriate) when the source supports it. Do not imply that station-based validation constitutes pixel-wise validation of all raster cells.

    For uncertainty products, also keep support scope separate from assessment context: a per-pixel BSE raster can have scope=per_pixel_or_local and evaluation_support=raster_cell, while PICP/MPIW can have scope=station_or_observation and assessment_context=cross_validated_interval_assessment.

13. SPATIAL SUPPORT FOR UNCERTAINTY PRODUCTS
    In data_quality_dependencies.uncertainty_handling.products_or_measures, distinguish a local/per-pixel uncertainty product from a spatial summary of that product using UncertaintyScope (for example per_pixel_or_local versus spatial_surface_summary).
    This UncertaintyScope rule does NOT mean that ValidationMetricRecord.scope should encode physical support. In the canonical quantitative metric ledger, use scope for the scientific target/aggregation and evaluation_support for raster/station/region/spatial-surface support.

14. UNCERTAINTY SEMANTICS
    Preserve explicit distinctions such as model-mean precision versus predictive uncertainty. Do not describe global summary tables as per-cell products.

15. DOI/RESOURCE SEMANTICS
    document_metadata.doi is only the DOI of the source document itself. Dataset, collection, input archive, software, workflow, vocabulary, and repository identifiers belong under related_resources. If the manuscript itself has no DOI, use null.

16. BENEFICIARIES / RECOMMENDATIONS
    Do not present inferred user groups or recommendations as explicit evidence. If conservatively inferred from application domains, mark the supporting evidence as inferred.

17. CONTROLLED NULLS
    Prefer null/unknown to a plausible but unsupported answer. In particular, do not fill input_data_requirements with producer inputs just to avoid nulls. Do not add undeclared fields.

18. ANALYSIS-TYPE CALIBRATION TERMINOLOGY
    Use analysis_type="model calibration" only when the analysed workflow itself calibrates/fits model parameters in a calibration sense. Do not select model_calibration merely because the paper discusses calibration as a potential downstream use. Use analysis_type="prediction-interval assessment" when the analysed task is evaluation of prediction-interval performance.

19. REVIEW STATUS
    All evidence extracted in this run is machine-generated. Use review_status=machine_extracted. Never claim human_verified or human_corrected; those states are reserved for a separate human-review stage and are enforced deterministically after extraction.

20. CANONICAL QUANTITATIVE METRIC LEDGER / ATOMIC METRIC RECORDS
    Treat validation_and_diagnostics.validation_metrics as the canonical quantitative metric ledger for this extraction.
    Use exactly one ValidationMetricRecord per metric, target, and aggregation scope. Never combine values from different
    targets or aggregation scopes in one record. For example, an all-crops MAE and a winter-wheat MAE must be two records,
    even when they appear in the same source table or sentence.

    scope_label must describe exactly one target. Do not use semicolon-separated/list-like labels. Use the most specific
    domain-appropriate scope: dataset/dataset_family for whole-dataset summaries, subgroup for a named population/category,
    variable_or_layer for one measured variable/product layer, study_or_site for one study/site, experiment_or_treatment for
    one experimental condition, model_or_method for one model/method, and spatial/temporal/spatiotemporal subset scopes where
    appropriate. Domain-specific crop/crop_phase/phase_year scopes are available when the paper is actually about those entities.

    Quantitative spatial BSE summaries and demonstrated downstream quantitative metrics should also be represented in this
    canonical metric ledger using their appropriate context. Do not independently populate
    outputs_and_fitness_indicators.fitness_for_use_metrics.producer_side_metrics or application_specific_metrics; leave those
    lists null. The pipeline derives them deterministically from the canonical ledger after extraction so values cannot diverge.

21. BENEFICIARIES
    Populate application_profile.beneficiaries only when the source explicitly names or directly identifies beneficiary/user
    groups. Do not infer beneficiary groups merely from listed application domains or potential uses. If beneficiaries are only
    inferable, leave application_profile.beneficiaries null; provenance may note that the source does not explicitly enumerate them.

22. ATOMIC SPLITTING MUST BE LOSSLESS
    When one authored table, sentence, or caption reports several distinct quantitative statistics, emit every supported
    statistic as its own canonical ValidationMetricRecord. Splitting a mixed source statement into atomic records must not
    discard sibling metrics or sibling targets. Examples: if a table supports both MAE and RMSE for the same target, create
    both records; if it supports both PICP and MPIW, create both records; if it supports all-crop and crop-specific values,
    create separate records for each target/scope.

    Do not choose only the most prominent number. Preserve all substantively relevant quantitative metrics explicitly supported
    by the source when they belong to the DFFP dimensions represented by this schema.

23. METRIC SCOPE CONSISTENCY
    scope=dataset_family is only for a genuine family/collection-wide summary. A named subset, category, variable, site, treatment,
    model or method must use a corresponding specific scope. Domain-specific crop/crop_phase/phase_year scopes are conveniences,
    not assumptions about the document. Never use a physical support label (raster surface, station, pixel) as the scientific target
    scope when evaluation_support already records that support.

24. QUANTITATIVE METRIC EVIDENCE IS REQUIRED
    Every ValidationMetricRecord must include at least one evidence record. Reuse the most direct authored table/prose/figure
    evidence and preserve source_item_id, source_page and source_location whenever the source bundle supplies them. Do not emit
    a numerical validation/uncertainty/use-case metric without evidence.

25. DOWNSTREAM QUANTITATIVE METRICS BELONG IN THE CANONICAL LEDGER
    Demonstrated downstream quantitative results (context=downstream_use_case), such as a numerical result from an application, case study, worked example, or proof-of-concept,
    belong in validation_and_diagnostics.validation_metrics as canonical records with scope=use_case and appropriate evidence.
    The pipeline will derive application_specific_metrics from them. Do not omit such a metric merely because it is not a
    producer validation statistic.

26. MODEL-CALIBRATION LEAKAGE
    Do not classify the analysed workflow as analysis_type="model calibration" solely because the manuscript lists calibration
    or parameterisation as a potential downstream application. Use "model calibration" only when calibration is
    actually performed within the analysed producer workflow itself and is supported by workflow/method evidence.

27. PICP / MPIW TERMINOLOGY
    PICP is empirical coverage; MPIW is interval width/sharpness. When mentioning them together in normalized semantic fields,
    use "coverage and width" or "coverage and sharpness", not a generic phrase such as "coverage diagnostics" that obscures
    MPIW's width meaning. Never generate "prediction-interval calibration" in normalized fields.

28. SOURCE ITEM REGISTRY / LOCATORS
    The source bundle contains a deterministic source-item registry. When citing a structured table, figure, or formula,
    select the stable source_item_id from that registry. Do not guess page numbers or item labels. The pipeline will inject
    source_page/source_location deterministically and will normalize source_section when a conservative section_hint exists.
    For structured evidence, source_item_id is therefore more important than inventing a prose-like section locator.

29. QUANTITATIVE COMPLETENESS CHECKLIST
    Before finalizing validation_and_diagnostics.validation_metrics, inspect the QUANTITATIVE METRIC CANDIDATE HINTS in the
    source bundle. They are discovery hints, not fitness judgments and not permission to invent unsupported metrics.

    If you choose a target represented by a structured table row, preserve all substantively relevant metric-like sibling columns
    supported in that selected row, including paper-specific metrics not listed in this prompt. The canonical ledger should be
    lossless for selected targets rather than retaining only familiar metric names.

    Also retain explicit summary-level quantitative uncertainty/quality statements from prose or captions and explicit numerical
    demonstrated downstream-use results when those are present and DFFP-relevant. Give each its own atomic record,
    appropriate context/scope/evaluation_support, and direct evidence.

30. FINAL SELF-CHECK BEFORE OUTPUT
    Verify all of the following before returning the structured record:
    - Every metric uses the most specific scientific target scope supported by the paper; physical/statistical support stays in evaluation_support.
    - When selected evidence reports multiple quality/uncertainty metrics for one target, sibling metrics are retained losslessly.
    - Summary-level numerical uncertainty/quality statements are not omitted merely because they occur in prose/captions rather than tables.
    - Demonstrated downstream numerical results are represented with context=downstream_use_case.
    - analysis_type does not contain model calibration unless producer workflow evidence shows actual calibration.
    - No normalized field uses prediction-interval calibration terminology.


31. CROSS-DOCUMENT / DOMAIN-AGNOSTIC CONTRACT
    This pipeline is intended for heterogeneous scientific papers. Never assume that entities, metrics, sections, units,
    models, crops, regions, variables, thresholds, or use cases from a previous document apply to this document. Examples
    in this prompt illustrate schema semantics only. Extract only what the current source bundle supports.

32. GENERIC METRIC CANDIDATES
    QUANTITATIVE METRIC CANDIDATE HINTS may contain familiar metrics or paper-specific names discovered from metric-like
    table headers and explicit name/value prose. Treat candidate names and values as discovery aids only. Preserve the
    authored name when no controlled/common alias is appropriate; do not force every paper into MAE/RMSE/PICP/MPIW/BSE.

33. MULTI-MODAL COMPLETENESS
    Quantitative evidence may occur in authored tables, prose, captions, figures, or formulas. Do not privilege tables so
    strongly that summary-level quality/uncertainty/application results from other authored modalities disappear. At the
    same time, do not enumerate every number in a results section: prioritize DFFP-relevant summary, validation, quality,
    uncertainty, diagnostic, and demonstrated-application quantities.

34. SOURCE-ITEM IDs ARE MODALITY-SPECIFIC
    Use source_item_id only when the evidence itself is the structured table/figure/formula/caption. For ordinary authored
    prose, cite the prose section/text directly and leave source_item_id null; do not attach a nearby equation or figure ID
    merely because it appears on the same page.

35. SUPPORT IS NOT TARGET SCOPE
    A metric summarized over a raster/spatial surface, station set, region, or other physical support still needs a scientific
    target scope when one is named. Put physical/statistical support in evaluation_support. For example, a summary of a named
    variable/layer over a spatial surface should use scope=variable_or_layer (or another more specific domain scope) together
    with evaluation_support=spatial_surface, rather than using spatial_surface_summary as a substitute for the target.
